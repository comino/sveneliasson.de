ClickHouse Compression Codecs for Time-Series Data: A Benchmark

  • clickhouse
  • compression
  • time-series
  • benchmark

Abstract

We benchmark five compression codec configurations on 100 million rows of synthetic time-series data in ClickHouse 25.11. The configurations range from default LZ4 to per-column specialized codecs (DoubleDelta, Delta, Gorilla) with ZSTD(3) and ZSTD(9) as general-purpose compressors. We measure storage (via system.parts_columns), query latency (10 queries × 10 runs, cold and warm, median ± IQR), and ingest throughput (3 batch sizes × 10 runs). Key findings: (1) Per-column codecs with ZSTD(3) achieve 4.23× overall compression vs 1.67× for default LZ4, driven by 872× on sorted timestamps and 843× on monotone counters. (2) Raising ZSTD from level 3 to 9 adds no measurable compression benefit but reduces ingest throughput by 28% at 1M-row batches (37% below default LZ4). (3) Better compression does not consistently improve query speed: V4 wins on well-compressed columns (counter aggregation: 819 ms vs 905 ms) but loses on poorly-compressed ones (value scans: 480 ms vs 401 ms). (4) Gorilla codec expands noisy float data and should only be used on smooth, slowly-changing values. We provide a decision tree for codec selection and discuss limitations of our synthetic, single-part, fits-in-RAM setup.

Setup

  • Server: Hetzner CX53 with 16 vCPU (AMD EPYC), 32 GB RAM, 320 GB NVMe SSD
  • ClickHouse: 25.11.3.54
  • Dataset: 100M rows × 6 columns, simulating Prometheus-style metrics
  • Runs: 10 per query per variant. We report median ± IQR (interquartile range).
  • Cold runs: Between each cold measurement, all caches were dropped: 
    clickhouse-client -q "SYSTEM DROP FILESYSTEM CACHE"
clickhouse-client -q "SYSTEM DROP MARK CACHE"
clickhouse-client -q "SYSTEM DROP UNCOMPRESSED CACHE"
sync; echo 3 > /proc/sys/vm/drop_caches
  • Warm runs: One warmup query (same SQL, result discarded) to populate OS page cache and ClickHouse mark cache, then 10 measured runs without cache drops. All runs execute sequentially via clickhouse-client --time --format=Null. The warmup ensures data is in the OS page cache; subsequent runs predominantly measure decompression CPU + query processing, with minimal I/O (page faults and FS metadata may still contribute). Note: “predominantly CPU-bound” means decompression is the largest measured contributor, not that I/O is zero. Thread scheduling, memory allocation, and other factors still contribute.
  • Query order: Fixed (Q1–Q10 per variant), not randomized. Given the per-query cache drops for cold runs, ordering effects are minimal. Warm runs use the same fixed order after a single warmup pass. A limitation: warm-run ordering could introduce systematic bias from cache residency of previous queries. We did not test randomized order; see Limitations.
  • “Uncompressed” throughout this article refers to data_uncompressed_bytes from system.parts_columns. This is ClickHouse’s internal uncompressed column data size. It excludes mark files (marks_bytes), primary key index, and other metadata.
  • Cold/warm caveat: The entire dataset (543 MB compressed for V4, 1.37 GB for V1) fits within the 32 GB server RAM. “Cold” means we dropped all ClickHouse and OS caches, but the OS can re-cache data from NVMe during a query. True I/O-bound behavior would require a dataset exceeding available memory. Our cold measurements primarily show the overhead of re-reading from NVMe + decompression, not sustained random I/O. In a production system where data exceeds RAM, compression’s I/O reduction would matter more: V4’s 543 MB requires ~2.5× fewer disk reads than V1’s 1.37 GB. Our results underestimate this advantage.

Data Generation

The dataset contains 100M rows generated with ClickHouse’s numbers() table function:

INSERT INTO exp01_compression.source
SELECT
    toDateTime('2024-01-01 00:00:00') + intDiv(number, 50) AS timestamp,
    ['cpu_usage','disk_io','http_requests_total','mem_free','net_bytes_sent']
        [1 + (number % 5)] AS metric_name,
    50 + 30 * sin(number / 1000.0) + (rand(number) % 1000) / 2000.0 AS value,
    concat('host-', toString(number % 50)) AS host,
    ['us-east','us-west','eu-central','ap-south'][1 + (rand(number + 1) % 4)] AS region,
    intDiv(number, 50) AS counter
FROM numbers(100000000);

This produces:

  • 5 distinct metric_name values (LowCardinality(String))
  • 50 distinct host values (LowCardinality(String))
  • 4 distinct region values (LowCardinality(String))
  • timestamp: DateTime, 1-second intervals (50 rows/second across 5 metrics × 10 hosts × …), spanning 2024-01-01 to 2024-04-25 (~115 days)
  • counter: UInt64, monotonically increasing (shared across all series at same timestamp)
  • value: Float64, sin(t) + uniform_noise(0, 0.5), simulating a noisy gauge

All tables use ORDER BY (metric_name, host, timestamp) and default index_granularity = 8192. After INSERT, OPTIMIZE TABLE … FINAL merged each table into a single part.

Data regularity check: timestamp intervals are strictly 1-second within each (metric_name, host) group (verified: SELECT max(diff) FROM (SELECT timestamp - lag(timestamp) OVER (...) AS diff ...) = 1 second). counter is strictly monotone (no violations). These ideal conditions produce the extreme compression ratios reported below. Real data with variable intervals or out-of-order inserts will compress less.

The full generator script is in 01/scripts/generate_data.sql.

Codec Variants (DDL)

-- V1: Default (LZ4)
CREATE TABLE v1_default (
    timestamp DateTime,
    metric_name LowCardinality(String),
    value Float64,
    host LowCardinality(String),
    region LowCardinality(String),
    counter UInt64
) ENGINE = MergeTree()
ORDER BY (metric_name, host, timestamp);

-- V2: ZSTD(3) on all columns
CREATE TABLE v2_zstd (
    timestamp DateTime CODEC(ZSTD(3)),
    metric_name LowCardinality(String) CODEC(ZSTD(3)),
    value Float64 CODEC(ZSTD(3)),
    host LowCardinality(String) CODEC(ZSTD(3)),
    region LowCardinality(String) CODEC(ZSTD(3)),
    counter UInt64 CODEC(ZSTD(3))
) ENGINE = MergeTree()
ORDER BY (metric_name, host, timestamp);

-- V3: Per-column specialized + LZ4
CREATE TABLE v3_percolumn (
    timestamp DateTime CODEC(DoubleDelta, LZ4),
    metric_name LowCardinality(String) CODEC(LZ4),
    value Float64 CODEC(Gorilla(8), LZ4),  -- Gorilla(8): 8 = sizeof(Float64)
    host LowCardinality(String) CODEC(LZ4),
    region LowCardinality(String) CODEC(LZ4),
    counter UInt64 CODEC(Delta(8), LZ4)
) ENGINE = MergeTree()
ORDER BY (metric_name, host, timestamp);

-- V4: Per-column specialized + ZSTD(3)
CREATE TABLE v4_percolumn_zstd (
    timestamp DateTime CODEC(DoubleDelta, ZSTD(3)),
    metric_name LowCardinality(String) CODEC(ZSTD(3)),
    value Float64 CODEC(Gorilla(8), ZSTD(3)),
    host LowCardinality(String) CODEC(ZSTD(3)),
    region LowCardinality(String) CODEC(ZSTD(3)),
    counter UInt64 CODEC(Delta(8), ZSTD(3))
) ENGINE = MergeTree()
ORDER BY (metric_name, host, timestamp);

-- V5: Aggressive: same pre-codecs as V4, ZSTD(9) on most columns
CREATE TABLE v5_aggressive (
    timestamp DateTime CODEC(DoubleDelta, ZSTD(9)),
    metric_name LowCardinality(String) CODEC(ZSTD(9)),
    value Float64 CODEC(Gorilla(8), ZSTD(3)),  -- ZSTD(3), not (9): see note
    host LowCardinality(String) CODEC(ZSTD(9)),
    region LowCardinality(String) CODEC(ZSTD(9)),
    counter UInt64 CODEC(Delta(8), ZSTD(9))
) ENGINE = MergeTree()
ORDER BY (metric_name, host, timestamp);

Notes on codec choices:

  • Gorilla(8): The parameter specifies the data type width in bytes. For Float64 = 8 bytes. This tells the Gorilla encoder to XOR consecutive 8-byte values, matching the native Float64 representation.
  • V3 uses per-column specialized codecs with LZ4 as the general-purpose back-end: DoubleDelta+LZ4 on timestamps, Gorilla(8)+LZ4 on value, Delta(8)+LZ4 on counter, plain LZ4 on LowCardinality strings. V4 replaces LZ4 with ZSTD(3) throughout.
  • V5 uses ZSTD(9) on most columns, but value uses ZSTD(3): the actual DDL on the server. ZSTD(9) on Gorilla-encoded noisy floats provides no benefit over ZSTD(3); ClickHouse applies the specified level, but the incompressible XOR residuals give the higher level nothing to work with. The V4≈V5 storage result (141 KB difference on 543 MB) confirms this.

Results: Storage

Measuring Compression

We query system.parts_columns on each table (single merged part after OPTIMIZE FINAL):

    table, column,
    data_compressed_bytes, data_uncompressed_bytes,
    round(data_uncompressed_bytes / data_compressed_bytes, 2) AS ratio,
    marks_bytes, rows
FROM system.parts_columns
WHERE database = 'exp01_compression' AND active = 1
ORDER BY table, column;

Why 872× on timestamps? The data is sorted by (metric_name, host, timestamp). Within each (metric_name, host) group, timestamps are strictly sequential at 1-second intervals (2M consecutive timestamps per group). DoubleDelta on such data produces constant-zero second derivatives. ZSTD(3) then compresses the near-zero residuals to almost nothing.

This is the best case for DoubleDelta. Real timestamps with variable intervals, out-of-order inserts, or different sort keys will compress much less.

V1’s timestamp column (plain LZ4, no pre-codec) achieves only 1.0× because LZ4 cannot exploit the sequential structure without Delta/DoubleDelta pre-processing.

Why 843× on counters? Same principle. counter increases monotonically. Delta(8) produces small, regular residuals that ZSTD compresses efficiently.

Why value barely compresses? The column contains sin(t) + uniform_noise. The noise prevents both LZ4 and Gorilla from finding patterns. V4 (Gorilla+ZSTD) achieves 1.48×, marginally better than V1’s 1.45×. Critically, V3 (Gorilla+LZ4) achieves only 1.26×, worse than V1’s plain LZ4. Gorilla’s XOR overhead expands the data, and LZ4 can’t recover it. ZSTD partially compensates in V4, but the improvement is negligible. See the Gorilla deep-dive below.

V3 codec detail: V3 applies per-column codecs as shown in the DDL above: DoubleDelta+LZ4 on timestamp (839×), Gorilla(8)+LZ4 on value (1.26×), Delta(8)+LZ4 on counter (818×), and plain LZ4 on the three LowCardinality string columns (212–213×). The dramatic ratios on timestamp and counter come from the pre-codecs (DoubleDelta, Delta) reducing regular patterns to near-zero residuals; even LZ4 compresses those efficiently. The difference between V3 and V4 is almost entirely in ZSTD’s superior handling of the residuals that LZ4 leaves on the table.

Gorilla Deep-Dive: XOR Encoding and When It Helps

Gorilla (Pelkonen et al., VLDB 2015) compresses floating-point values using XOR-based delta encoding. For each value, it XORs with the previous value and encodes only the differing bits. When consecutive values are similar (small XOR delta), only a few bits change, leading to excellent compression. When values change unpredictably (large XOR delta), nearly all 64 bits differ, and Gorilla adds encoding overhead on top of the raw data.

To isolate the effect, we tested four value distributions on separate 10M-row tables, comparing V1 (LZ4 default) vs V3 (Gorilla+LZ4) on the value column:

DistributionDescriptionV1 LZ4 RatioV3 Gorilla+LZ4 RatioGorilla Benefit
Monotonef(t) = t × 0.0011.74×44.7×25.7× better
Spiky99% zeros, 1% random spikes1.62×30.8×19.0× better
Sinus + noisesin(t/1000) + uniform_noise1.31×2.48×1.9× better
Randomrand() uniform Float641.05×1.29×1.2× better

Source: system.parts_columns on dist_{name}_v1 and dist_{name}_v3 tables, value column only. 10M rows each, sorted by timestamp, single part after OPTIMIZE FINAL.

Key insight: Gorilla excels when consecutive stored values are nearly identical (monotone, mostly-zero). On smoothly drifting data, it helps moderately. On fully random data, the benefit is marginal. On the main benchmark’s noisy gauge data, Gorilla actually hurts in V3 (1.26×) because the LZ4 back-end handles the Gorilla-expanded data less efficiently than raw float data.

In V4 (Gorilla+ZSTD), the value column achieves 1.48×, slightly better than V1’s 1.45×, because ZSTD can partially recover from Gorilla’s expansion. But the improvement is negligible.

When to use Gorilla:

  • ✅ Battery levels, slowly-drifting temperatures, monotone counters as floats
  • ✅ Sparse data with many repeated values (e.g., 99% zeros)
  • ❌ Noisy gauge metrics (CPU%, latency, throughput)
  • ❌ Random or uniformly distributed values

Results: Query Performance

Benchmark Queries

We run 10 queries covering different access patterns: point lookups, range scans, aggregations, percentiles, distinct counts, argMax, and window functions.

-- Q1: Point lookup (1 host, 1 hour): tests primary key selectivity
SELECT avg(value) FROM {table}
WHERE metric_name='cpu_usage' AND host='host-0'
  AND timestamp BETWEEN '2024-01-01 00:00:00' AND '2024-01-01 01:00:00';

-- Q2: Range scan (1 metric, 7 days): medium selectivity
SELECT avg(value) FROM {table}
WHERE metric_name='cpu_usage'
  AND timestamp BETWEEN '2024-01-01' AND '2024-01-08';

-- Q3: Top-K GROUP BY host: aggregation with grouping
SELECT host, count(), avg(value) FROM {table}
WHERE metric_name='cpu_usage'
GROUP BY host ORDER BY count() DESC LIMIT 10;

-- Q4: Point lookup (1 host, 1 hour, multi-agg): minimal data
SELECT avg(value), min(value), max(value) FROM {table}
WHERE metric_name='cpu_usage' AND host='host-3'
  AND timestamp BETWEEN '2024-01-05 12:00:00' AND '2024-01-05 13:00:00';

-- Q5: Full table scan with WHERE: touches value column
SELECT count() FROM {table} WHERE value > 60;

-- Q6: Multi-column aggregation: heavy, reads all columns
SELECT metric_name, host, avg(value), sum(counter) FROM {table}
GROUP BY metric_name, host ORDER BY avg(value) DESC LIMIT 20;

-- Q7: Percentile: quantile on value column
SELECT metric_name, quantile(0.99)(value) AS p99 FROM {table}
GROUP BY metric_name;

-- Q8: Distinct count: uniqExact on string columns
SELECT uniqExact(metric_name), uniqExact(host) FROM {table};

-- Q9: Last value per host: argMax pattern
SELECT host, argMax(value, timestamp) AS last_value FROM {table}
WHERE metric_name='cpu_usage' GROUP BY host;

-- Q10: Window function: moving average
SELECT timestamp, avg(value) OVER (ORDER BY timestamp
  ROWS BETWEEN 59 PRECEDING AND CURRENT ROW) AS ma60
FROM {table}
WHERE metric_name='cpu_usage' AND host='host-0'
  AND timestamp BETWEEN '2024-01-01' AND '2024-01-02'
ORDER BY timestamp;

Analysis

Cold vs warm patterns differ by variant. V1 (LZ4) shows the largest cold→warm improvement across most queries. Example: Q05 cold 229 ms → warm 16 ms (14× speedup). V4 (ZSTD): Q05 cold 243 ms → warm 86 ms (2.8× speedup). Why? V1 reads more raw bytes from disk (1.37 GB vs 543 MB) but LZ4 decompression is nearly free, so warm queries benefit enormously from OS page cache (data already decompressed at ~memory speed). V4 reads less data but pays ZSTD decompression CPU on every query, warm or cold. The decompression cost doesn’t disappear when data is cached.

Point lookups (Q01, Q04, Q10): all variants identical. These queries read 1–12 granules. At this scale, codec overhead is negligible. Q04 at 4 ms reads a single granule (~8K rows).

Value-heavy queries (Q05, Q07): V1 wins. Q07 (quantile) reads the value column across all rows. V1’s LZ4 on value (551 MB, 1.45× ratio) is faster than V4’s Gorilla+ZSTD on value (542 MB, 1.48× ratio) because LZ4 decompression is ~3× cheaper than ZSTD per byte. Since both variants store nearly the same bytes for value, the decompression CPU dominates.

Counter-heavy queries (Q06): V2/V4/V5 win cold, V1 wins warm. Q06 reads both value and counter. Cold: V4 (819 ms) beats V1 (905 ms) because counter is 420 MB in V1 vs 949 KB in V4, meaning less I/O. Warm: V1 (544 ms) beats V4 (639 ms) because decompressing counter from 949 KB ZSTD is slightly more overhead than reading from cache, and value decompression cost adds up.

Q09 (argMax): V3/V4/V5 win cold. This query reads timestamp, value, and host columns for one metric. V3/V4/V5 benefit from the heavily compressed timestamp column (459 KB vs 402 MB in V1), which reduces I/O substantially even for cold reads.

Q08 (uniqExact): all variants similar. uniqExact on LowCardinality columns is dictionary-bound. Since all variants store LowCardinality similarly (the dictionary is tiny), performance is nearly identical.

ProfileEvents: Testing Whether Decompression Dominates

To validate the claim that ZSTD decompression CPU dominates warm query latency, we collected ProfileEvents from system.query_log for Q05 (full table scan, warm, 5 runs each):

Both variants read the same rows and bytes (ClickHouse decompresses to the same internal format). Disk read time is similar (data cached). But V4 uses 6.8× more CPU, predominantly attributable to ZSTD decompression of the value column (541 MB, 1.48× ratio). For this query, with data in page cache, ZSTD decompression CPU is the dominant cost difference. We profiled Q05 only; the same mechanism is plausible for the other value-heavy queries but not individually verified (see Limitations).

Why read_rows = 40M, not 100M? ClickHouse automatically applies PREWHERE optimization: WHERE value > 60 is moved to a PREWHERE clause, which uses per-granule min-max statistics to skip granules where all value entries are ≤ 60. The data’s sinusoidal pattern creates granules where value stays entirely below 60 (approximately 60% of all granules). With PREWHERE disabled (PREWHERE 1 WHERE value > 60), read_rows rises to 100M (all 12,208 granules). The read_rows metric in system.query_log with PREWHERE reflects rows from selected granules, not total rows scanned. Both V1 and V4 select the same granules (~4,890 of 12,208), so the comparison remains valid. Full analysis: 01/data/v5/profileevents_explain.md.

Cold vs Warm: What “Cold” Means Here

The dataset (543 MB for V4, 1.37 GB for V1) fits within the 32 GB server RAM. After dropping caches, the OS reads data from NVMe SSD, and modern NVMe can deliver several GB/s sequentially. The practical difference between “cold” and “warm” is:

  • Cold: NVMe read latency + decompression CPU
  • Warm: Zero I/O + decompression CPU

For V1 (LZ4), decompression is nearly zero, so cold/warm mainly measures I/O. For V4 (ZSTD), decompression is the dominant cost regardless of cache state. This explains why V1 shows more dramatic cold→warm improvement.

In a production scenario where data exceeds RAM, the I/O advantage of better compression would be more significant: V4’s 543 MB would require fewer disk reads than V1’s 1.37 GB. Our results likely underestimate the cold-query benefit of V4 in real production.

Results: Ingest Throughput

Ingest Methodology

Each measurement inserts N rows from the source table into the target variant using INSERT INTO {target} SELECT ... FROM source LIMIT {batch_size} OFFSET {offset} via clickhouse-client (native protocol, single-threaded, max_insert_threads=1). Rows/s is computed as batch_size / elapsed_seconds where elapsed_seconds comes from clickhouse-client --time. Between runs, the target table is truncated (TRUNCATE TABLE). No concurrent inserts, no async inserts, no background merges were throttled. Format: native (no CSV/JSON parsing overhead). The 10 runs use non-overlapping offsets from the 100M source table to avoid caching effects.

At small batch sizes (10K), all variants perform similarly (~140K rows/s): per-INSERT overhead dominates. At 1M batches:

  • V1 (LZ4): 5.67M rows/s, fastest
  • V4 (per-col ZSTD): 4.96M rows/s, 12% slower than V1
  • V5 (ZSTD(9)): 3.56M rows/s, 28% slower than V4 and 37% slower than V1

V4 is only marginally slower than V1 at ingest because the pre-codec computation (Delta, DoubleDelta) is lightweight. The ZSTD(3) compression adds moderate CPU. V5’s ZSTD(9) adds significant CPU without improving compression: a clear lose-lose.

Surprise: V4 is slightly faster than V2 and V3 at 1M batches (4.96M vs 4.65M/4.81M). This may be an artifact of run-to-run variance (the IQRs overlap), or the pre-codecs may produce data that ZSTD(3) compresses more efficiently per CPU cycle than raw data.

Conclusion: Which Compression Wins?

V4 (per-column specialized + ZSTD(3)) offers the best storage-first trade-off for time-series workloads in ClickHouse, when minimizing disk footprint is the primary goal. It achieves 4.23× compression (2.5× better than default LZ4) while losing only 12% ingest throughput and delivering competitive cold query latency. However, V1 (LZ4) remains faster for warm queries on value-heavy access patterns, where ZSTD decompression CPU dominates.

Real-World Takeaways

  1. On this dataset, ZSTD(9) was dominated by ZSTD(3). Same compression, 28% slower ingest than ZSTD(3) with the same pre-codecs. The pre-codecs do the real work.
  2. Don’t apply Gorilla blindly to floats. It only helps on smooth, slowly-changing data. On noisy gauges (CPU, latency), it can make things worse.
  3. “Better compression = faster queries” is not always true. It depends on which columns the query reads. Compression helps I/O-bound columns (timestamps, counters) but ZSTD’s decompression CPU hurts on already-small columns (noisy floats).
  4. Measure on your data. Our extreme 800×+ ratios depend on perfectly regular 1-second intervals. Real Prometheus metrics with variable scrape intervals will see 10–100× on timestamps (still excellent, but not 872×).
  5. Per-column codec selection is the high-value activity. The difference between V1 (1.67×) and V4 (4.23×) is not ZSTD: it’s DoubleDelta on timestamps and Delta on counters. Choose codecs per column type.

Codec Decision Tree

Is your column a sorted timestamp?
  → Yes: DoubleDelta + ZSTD(3)                    [872× on sorted 1s intervals]
  → No: Is it a monotone counter?
    → Yes: Delta(8) + ZSTD(3)                      [843× on strictly monotone]
    → No: Is it a Float?
      → Smooth/slowly changing?  → Gorilla(8) + LZ4   [up to 45× on monotone floats]
      → Noisy/random?           → LZ4 default         [1.45×: Gorilla hurts]
    → String/LowCardinality?    → ZSTD(3)             [867–908×]

This is a starting point, not gospel. The ratios above are for this synthetic dataset with perfectly regular intervals and monotone counters. Real data will differ. Always measure on your own data with system.parts_columns.

Limitations

  1. Synthetic data. Real Prometheus metrics have different distributions (bimodal CPU, heavy-tailed latencies, quantized memory). The extreme 800–900× ratios on timestamp/counter depend on perfectly regular 1-second intervals and monotone counters. Validate on your own data.

  2. Single sort order. DoubleDelta’s extreme ratios require timestamps sorted contiguously. A different ORDER BY (e.g., (host, timestamp) without metric_name prefix) would produce different results.

  3. Single-query, single-thread benchmarks. Under concurrent load, ZSTD’s higher CPU cost during decompression may become more significant. Default max_threads=16 was used for all queries.

  4. Dataset fits in RAM. 100M rows produce ~543 MB (V4) to ~1.37 GB (V1) on a 32 GB server. Cold measurements still benefit from OS filesystem caching after the first NVMe read. The compression advantage would be more impactful when data exceeds available memory.

  5. No FPC codec tested. ClickHouse’s FPC codec (since 22.6) is designed for floating-point compression and may outperform both Gorilla and LZ4 on noisy floats.

  6. Single merged part. OPTIMIZE FINAL produces one large part, which is optimal for Delta/DoubleDelta. In production with many parts, per-part compression context is smaller and ratios may differ.

  7. No production settings tuned. Default max_threads, max_insert_threads, no async inserts, no custom block sizes. Query results reflect out-of-the-box behavior.

  8. Uniform noise distribution. Real gauge metrics often have Gaussian noise, bimodal distributions, or quantized values. Different noise distributions would affect Gorilla’s effectiveness differently.

  9. Fixed query order for warm runs. Warm benchmarks use the same Q1–Q10 order without randomization. Cache residency from previous queries could introduce systematic bias. We did not test randomized order.

  10. ProfileEvents profiling is exemplary, not systematic. We profiled Q05 warm (V1 vs V4) via system.query_log to validate the decompression-CPU claim. A full profiling of all 10 queries × 5 variants would strengthen the causal interpretation for other query patterns, particularly the counter-heavy Q06 where cold and warm rankings diverge.

Query execution order: All 10 queries were run sequentially per variant, with cache drops between each cold measurement. No randomization of query order. Warm runs used the same fixed order.
