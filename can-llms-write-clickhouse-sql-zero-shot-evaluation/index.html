Can LLMs Write ClickHouse SQL? A Zero-Shot Benchmark of 22 Models

  • clickhouse
  • llm
  • sql
  • benchmark

ClickHouse SQL deviates from standard SQL in ways that matter for text-to-SQL: quantile(), arrayJoin(), -If combinators, WITH FILL, map and array functions. This benchmark measures how well current LLMs handle the dialect in the hardest setting: zero-shot, one attempt, no examples.

22 models, 50 questions, 3 runs per question, 3,300 scored queries total. Each generated query is executed against a live ClickHouse database and its output compared to a hand-written reference query.

Key results:

  1. Strict accuracy ranges from 60.0% to 74.0%. Claude Opus 5 leads at 74.0%, followed by Claude Sonnet 5 (73.3%) and Kimi K3 (72.7%). The whole field sits within 14 points.
  2. Most failures are not wrong SQL. Classifying every failed run: 82% of wrong-result queries in the August wave (87% in February) have correct logic and differ from the reference only in output format or column selection. Genuine logic errors are 5.2% of all runs in the most recent wave. Adjusted for this, accuracy ranges from 86.7% to 95.3%.
  3. Cost per correct query spans a factor of ~240 within the current lineup: $0.00016 (DeepSeek V4-Flash) to $0.038 (GPT-5.6-Sol-Pro).
  4. Price does not predict accuracy. GPT-5.6-Terra ($1/M input) scores higher than both GPT-5.5 and GPT-5.6-Sol ($5/M each). All three GPT-5.6 pro variants score lower on strict accuracy than their same-priced base models.

Data, scripts and charts: comino/blog-experiments/03.

Setup

Schema and data

Two tables, ~1M events and ~10K users of synthetic web analytics data. Data generation is deterministic (rand(number) seeding), so every evaluation runs against identical data.

CREATE TABLE events (
    event_id       UInt64,
    timestamp      DateTime64(3, 'UTC'),
    user_id        UInt64,
    event_type     LowCardinality(String),
    page           String,
    duration_ms    Nullable(UInt32),
    properties     Map(String, String),
    tags           Array(String),
    country        LowCardinality(String),
    device         LowCardinality(String),
    revenue_cents  Nullable(Int64)
) ENGINE = MergeTree()
ORDER BY (timestamp, user_id)
PARTITION BY toYYYYMM(timestamp);

CREATE TABLE users (
    user_id    UInt64,
    created_at DateTime64(3, 'UTC'),
    plan       LowCardinality(String),
    email      String,
    age        Nullable(UInt8),
    country    LowCardinality(String),
    metadata   Map(String, String)
) ENGINE = MergeTree()
ORDER BY user_id;

Questions

50 questions in 5 difficulty tiers. T1/T2 are standard SQL (SELECT, WHERE, GROUP BY). T3 requires ClickHouse-specific functions (quantile(), mapContains(), has(), -If combinators). T4 covers joins, CTEs and subqueries. T5 covers window functions, WITH FILL, argMax(), array lambdas.

Protocol

  • Zero-shot. The prompt contains the full DDL, a short data description, the question, and the instruction to respond with only the SQL query.
  • Temperature 0, seed 42, 3 runs per question, all models accessed through OpenRouter.
  • Known prompt flaw, kept for comparability across waves: the prompt states “~100K users”, the dataset has ~10K. No question depends on user cardinality.

The 22 models were measured in two waves: 8 models in February 2026 (ClickHouse 25.11, prices as of 2026-02-12) and 14 models in August 2026 (ClickHouse 26.1, prices as of 2026-08-10, Claude Sonnet 5 at introductory pricing). Reference outputs are identical across versions except one reference query that needed a syntax fix on 26.1 (see Methodology notes). Cost figures use OpenRouter list prices from the respective measurement date.

Scoring

Per run: 3 = executes, output matches the reference (whitespace normalization, row sorting for unordered results, 0.1% numeric tolerance). 2 = executes, output differs. 1 = runtime error. 0 = syntax error or API failure.

Strict matching penalizes queries that are logically correct but return different columns or formats. Every score-2 run is therefore classified by re-executing both queries and comparing outputs structurally:

  • format_mismatch: correct logic, different output format (row order, missing LIMIT, date type, approximate vs exact aggregate)
  • column_mismatch: correct logic, different column selection
  • logic_error: wrong SQL

The classifier is rule-based (row-subset detection for LIMIT differences, per-column multiset overlap for column selection, value tolerance for approximate aggregates). Validated against a manual classification of the February wave it agrees on 88% of rows; in the sampled disagreements the manual label was at fault more often than the rule (an example is in Methodology notes). Both waves are classified with the same rules.

Two metrics follow: strict accuracy (score 3 only) and adjusted accuracy (score 3 plus format and column mismatches). Strict answers “does the output drop into an automated pipeline unchanged”; adjusted answers “is the SQL logically correct”.

Accuracy by difficulty tier

The tier structure is consistent across all 22 models: T1 is at or near 100% everywhere, T2 at 80 to 100%, and accuracy drops sharply at T3 where dialect-specific functions begin. T5 is hardest for every model; no model exceeds 43%. The differentiator between models is dialect knowledge, not SQL in general.

Cost vs performance

The vertical spread at any given cost level is the notable feature of this chart. Within the August wave:

  • GPT-5.6-Luna ($0.10/M in, $0.60/M out) reaches 66.0% strict / 94.0% adjusted at $0.0002 per correct query.
  • DeepSeek V4-Flash ($0.08/M in) reaches 62.7% / 92.0% at $0.00016 per correct query, the lowest in the field.
  • Claude Sonnet 5 delivers 73.3% at $0.0029 per correct query; Claude Opus 5 adds 0.7 points for 2.7× that.
  • GPT-5.6-Sol-Pro combines the second-lowest August strict accuracy with by far the highest cost ($0.038 per correct query, driven by long outputs at $30/M).

The pro variants of the GPT-5.6 series are priced identically to their base variants and scored lower in all three tiers (Terra 71.3 vs Terra-Pro 70.0, Luna 66.0 vs 64.7, Sol 65.3 vs 63.3). The mid-tier Terra also scored above the flagship Sol by 6 points. For this workload, neither the “pro” designation nor the price tier is a useful accuracy signal within that family.

For a pipeline that can validate and retry, the cost-efficient end of the field changes the calculus: at $0.0002 per correct query, five retries of a budget model cost 2% of a single flagship attempt.

What the failures are

August wave, 2,100 runs: 1,436 correct (68.4%), 623 wrong result, 38 runtime errors, 3 syntax or API errors. Classification of the 623 wrong results:

The February wave has the same structure (184 format, 159 column, 53 logic out of 1,200 runs). In both waves, the large majority of “wrong” results are queries whose filtering, aggregation and join logic is correct but which return different columns, different row ordering, or a different value format than the reference.

Consequences:

  • The strict ranking above partly measures “which model guesses the reference’s output conventions”. The 20 to 30 point strict-adjusted gap is consistent across every model.
  • For production text-to-SQL, specifying the expected output columns, ordering and LIMIT in the prompt recovers most of that gap. This has a larger effect than any model choice in this table.

Persistently failed questions

13 of the 50 questions had 0% strict accuracy across all February models. Under the August wave, 11 of the 13 remain at or near zero, and the classifier attributes them to format and column-selection differences rather than wrong logic. Two changed:

  • t5_06 (WITH FILL): 0% in February, 93% in August. The February models did not know this ClickHouse-only syntax; the August models do. This is the clearest genuine capability difference between the waves.
  • t4_10 (CTE + tuple subquery): 0% to 88%, same pattern.

Two questions are failed by all 22 models across both waves:

  • t5_07: “collect all event types per user into a sorted array”. The reference deduplicates; most models return duplicates. These are genuine logic errors.
  • t5_10: tag matching where the reference uses a substring match (LIKE '%premium%') and every model uses exact matching. The question wording (“with tag ‘premium’”) does not clearly imply substring semantics; this is at least partly a question defect.

Methodology notes

Three items surfaced while preparing this report. All three affect published numbers and are part of why the raw data is public.

Reference SQL is itself subject to dialect drift. The February reference for t5_06 used WITH FILL FROM '2024-01-01' with string literals. ClickHouse 25.11 accepted this; 26.1 requires typed constants and rejects the query. The first August scoring pass compared answers against a failing reference and marked 40 correct runs wrong. The published scores use a version-portable reference (toDate('2024-01-01')), which produces identical output on both versions.

The manual failure classification contained errors. An earlier draft of this evaluation claimed all 8 February models made the same logic error on t5_07 by failing to deduplicate. The response data shows 4 of the 8 deduplicated correctly (groupUniqArray, arrayDistinct) and differed only in a missing LIMIT or extra columns. The automated classifier caught the discrepancy; the manual labels did not. This motivated replacing manual classification with the rule-based classifier for both waves.

Measurement dates differ between waves. February models were measured 2026-02-12 on ClickHouse 25.11; August models 2026-08-10 on 26.1.2. Provider-side model updates between those dates are not observable through the API. Comparisons across waves (for instance, successor models scoring 2 to 11 points above their February counterparts) should be read with that caveat; comparisons within a wave are clean.

Model choice

Read from the table, for this workload:

  • Highest accuracy: Claude Opus 5, with Claude Sonnet 5 one run behind at roughly a third of the cost per correct query.
  • Accuracy per dollar in the upper group: GPT-5.6-Terra, within 3 points of the leader at an eighth of its cost per correct query.
  • High-volume pipelines with validation and retry: GPT-5.6-Luna or DeepSeek V4-Flash.
  • The GPT-5.6 pro variants are not competitive on this task at any budget.

Independent of model choice: constrain the output format in the prompt. The data shows format and column-selection divergence, not SQL capability, is the dominant failure mode for every model tested.

Limitations

  1. Sample size. 50 questions × 3 runs. One question is 2 points of strict accuracy; adjacent table rows are statistical ties.
  2. Strict scoring conflates format matching with capability. Quantified via the classification, but the classifier itself has a gray zone (for example, an hour-of-day returned as an integer instead of a timestamp), and its 88% agreement with manual labels bounds the precision of the adjusted numbers.
  3. Two measurement dates, two ClickHouse versions. Within-wave comparisons are clean; cross-wave comparisons carry the caveats above.
  4. Zero-shot only. Few-shot prompting with dialect examples would likely raise all T3+ scores.
  5. Small dataset. 1M rows. A February side-analysis found LLM-generated queries perform at parity with hand-written references (median speedup 1.0×); not re-measured in August.
  6. Synthetic questions and data, not calibrated against Spider/BIRD or production query logs.
